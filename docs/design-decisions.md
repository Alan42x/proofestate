# Architecture and Design Decisions

This document records ProofEstate's architectural decisions, alternatives, and trade-offs. It consolidates the design rationale and architecture comparison for a prototype that demonstrates one proof-backed lending rule end to end. Comparisons describe mechanisms; they are not measured performance baselines.

## Decision Summary

| Decision | Selected approach | Main rationale |
| --- | --- | --- |
| Execution environment | Ethereum-compatible smart contracts | Mature verifier tooling, reproducible local chain, public testnet path |
| Proof system | Groth16 | Small proof size and low verifier gas |
| Circuit language | Circom | Mature educational tooling and snarkjs integration |
| Commitment hash | MiMC Sponge | Efficient inside arithmetic circuits |
| Registry integration | Centralized Oracle over mock dataset | Keeps project focused on privacy-preserving compliance, not registry infrastructure |
| Compliance scope | One LTV rule | Narrow, auditable, and defensible proof statement |
| Deployment evidence | Localhost first, Sepolia optional | Deterministic functional tests and repeatable local measurements |
| Collateral model | One active loan per property | Prevents duplicate active borrowing with minimal state |

## Ethereum-Compatible Contracts

ProofEstate uses Solidity contracts running on a Hardhat local chain, with optional Sepolia deployment.

Rationale:

- Ethereum has mature tooling for compiling, testing, deploying, and inspecting smart contracts.
- Groth16 Solidity verifiers generated by snarkjs can be integrated directly.
- Hardhat provides deterministic local execution, which is better for dissertation reproducibility than depending on public testnet conditions.
- Sepolia remains useful for public transaction evidence, but it is not treated as the canonical benchmark environment.

Alternatives considered:

- A private permissioned chain would reduce public-chain complexity but weaken relevance to public verifiable lending workflows.
- A conventional backend database would be easier to build but would not demonstrate on-chain verification or auditable state transitions.
- A fully production Ethereum deployment would require real asset movement, registry integration, monitoring, and governance beyond the MVP scope.

Trade-off:

The system gains verifiable execution and clear auditability, but accepts Ethereum gas cost and smart contract immutability constraints.

## Groth16 Proof System

ProofEstate uses Groth16 for the LTV compliance proof.

Rationale:

- Groth16 has compact proofs and low on-chain verification cost.
- Circom and snarkjs provide a complete prototype toolchain.
- The generated Solidity verifier is small enough to deploy in the MVP.
- The proof statement is fixed and narrow, making a circuit-specific setup acceptable for dissertation demonstration.

Alternatives considered:

- PLONK-style systems offer more flexible setup assumptions, but add tooling and verifier complexity.
- STARK-style systems avoid trusted setup, but typically have larger proofs and more complex verifier integration for this MVP.
- Plaintext on-chain verification would be much simpler, but would reveal valuation and principal.
- An off-chain-only service could keep inputs private with appropriate access controls, but would not provide on-chain proof enforcement.

Trade-off:

Groth16 supports efficient on-chain verification, but it introduces a trusted setup assumption. This is documented as a limitation and is not presented as production security.

## MiMC Commitments

The circuit uses MiMC Sponge commitments:

```text
valuationCommitment = MiMC(propertyKeyField, propertyValue, valuationSalt)
principalCommitment = MiMC(propertyKeyField, loanPrincipal, principalSalt)
```

Rationale:

- MiMC is efficient in arithmetic circuits compared with hashes designed for conventional CPUs.
- circomlib provides a standard implementation.
- Including `propertyKeyField` binds each commitment to a specific property context.
- The chain stores commitments rather than plaintext valuation or principal. Commitment hiding additionally depends on secret, suitable randomness and surrounding interfaces.

Alternatives considered:

- Keccak is natural on Ethereum, but expensive inside Circom circuits.
- Poseidon is also ZK-friendly and would be a reasonable alternative, but MiMC was already supported by the chosen library stack.
- Publishing plaintext values would remove commitment complexity but fail the privacy objective.

Trade-off:

MiMC is selected for arithmetic-circuit suitability. The implementation does not establish application-wide confidentiality: its valuation salt is deterministic, and its mock registry and unauthenticated API expose witness values. No measured MiMC/Poseidon/Keccak comparison is reported.

## Centralized Oracle Service

The Oracle service reads the mock registry, evaluates registry eligibility rules, builds proof inputs, generates proofs, and optionally writes verification/compliance state on-chain.

Rationale:

- Real land registry integration is out of scope.
- The Oracle isolates off-chain facts from on-chain enforcement.
- Centralization keeps the prototype reproducible and easy to demonstrate.
- The limitation is explicit: the Oracle is trusted for registry interpretation.

Alternatives considered:

- A threshold oracle network would reduce trust in one service, but would become a separate systems project.
- Direct user-provided registry data would be easier, but would weaken the property verification story.
- On-chain registry storage would simplify proof binding but would expose more data and require unrealistic registry assumptions.

Trade-off:

The MVP accepts centralized oracle trust to keep the dissertation focused on zero-knowledge compliance and smart contract enforcement.

## Single LTV Rule

The circuit proves exactly:

```text
loanPrincipal * 10000 <= propertyValue * 8000
```

Rationale:

- One rule can be specified, implemented, tested, benchmarked, and defended rigorously.
- LTV is a realistic lending constraint and a clear privacy case because both valuation and principal may be sensitive.
- Additional business rules would make the prototype broader but less defensible.

Alternatives considered:

- A multi-rule compliance circuit would be closer to production underwriting, but would complicate testing and trusted setup.
- A generic policy circuit would be flexible, but harder to explain and benchmark.

Trade-off:

The system is intentionally narrow. Production compliance would require more rules, identity checks, and risk controls.

## Public Signal Binding

`ComplianceVerifier` checks all public signals before accepting a proof:

- property key field;
- valuation commitment;
- principal commitment;
- max LTV basis points.

Rationale:

- A valid proof is not enough by itself; it must be valid for the target on-chain property record.
- Binding prevents proof reuse across property IDs, valuation commitments, principal commitments, or LTV thresholds.
- The lending contract later checks `isCompliantFor(propertyId, principalCommitment)`, preserving the binding into loan approval.

Trade-off:

The verifier becomes more application-specific, but the security argument becomes much stronger.

## One Active Loan Per Property

`Lending` stores an active loan lock per property while a loan is `Requested` or `Approved`.

Rationale:

- The demo needs to prevent duplicate borrowing against the same collateral.
- The one-lock model is easy to reason about and test.
- The lock is released on `Rejected`, `Cancelled`, or `Repaid`.

Alternatives considered:

- Multiple loan tranches would be more flexible but require exposure accounting.
- A portfolio-level risk engine would be more realistic but outside the scope of the ZK LTV prototype.

Trade-off:

The lock is simple and defensible, but it does not model complex production lending products.

## Local Reproducibility First

Localhost is the canonical evidence environment.

Rationale:

- It avoids Sepolia faucet, RPC, congestion, and wallet instability.
- It makes tests, gas snapshots, demo runs, and benchmarks repeatable.
- It supports dissertation review without relying on external infrastructure.

Sepolia remains useful as optional public validation, especially for demonstrating that the same contracts can be deployed and inspected publicly.

Trade-off:

Local evidence is less externally visible than Sepolia transaction hashes, but it is more reproducible and more appropriate for benchmark claims.

## Architecture Comparison

The following comparison concerns disclosure and enforcement capabilities. Alternative implementations, matched latency/gas measurements, and production-readiness ratings have not been evaluated.

| Alternative | Financial data disclosure | Enforcement | Main dependency |
| --- | --- | --- | --- |
| Plaintext on chain | Values appear in public calldata or storage | Contract evaluates the inequality | Correct and authentic source values |
| Off-chain only | Backend confidentiality depends on access controls | Backend decision; no independent on-chain proof | Backend operator and database |
| ProofEstate Groth16 | Plaintext omitted from chain; registry/API disclose values and valuation hiding is not established | Contract verifies the proof and application binding | Honest oracle, uncompromised setup, commitment binding, maintained roles |
| PLONK-style proof | Can omit witness values; commitment and interface disclosure still require analysis | Requires an integrated verifier and binding checks | Specific setup model, source authenticity, verifier implementation |
| STARK-style proof | Can omit witness values; surrounding disclosure still requires analysis | Requires an integrated verifier and binding checks | Specific hash/proof assumptions and verifier implementation |
| Threshold oracle | Oracle distribution alone does not protect witness values | Depends on attestation and contract integration | Honest threshold, committee governance, coordination and disputes |
| On-chain registry | Plaintext records are public; commitments need a separate hiding analysis | Contract-readable source state | Authentic update authority and freshness policy |

The prototype selects Groth16 and a centralized mock-registry oracle to keep the implemented path reproducible. This does not establish a speed advantage or a production-security ranking. Threshold attestations would add committee membership, aggregation, signer coordination, monitoring, and dispute handling. A commitment registry would still require an authenticated writer and an explicit freshness policy.
